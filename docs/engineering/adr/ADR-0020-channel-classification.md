# ADR-0020: 节点数据通道分类（`observe` / `ops-read` / `control`）

- 状态：已接受（C1；为 C2 提供规则，不含 C2 的实现）
- 日期：2026-11-17
- 决策者：主人
- 关联：ADR-0007（host-ops 经 Hub 走 SSH）、ADR-0009（运维数据只经实时通道）、
  ADR-0010（10s 快照轮询）、ADR-0012（连接方案选择）、PR #75 提案、PR #76 通道梳理
- 补充：ADR-0009 中「哪些数据可以直连」只以快照特例体现，本 ADR 把它变成成文规则

## 背景

「哪些数据走浏览器直连、哪些经控制面」目前没有成文规则，只散落在两处特例里：
ADR-0010 允许快照直连，ADR-0007 规定 host-ops 的 Peer 调用要经 Hub。

实际后果：

1. **新增功能时只能靠写代码的人自己判断**，判断依据（只读、含不含机密、要不要跨节点）
   没有写在任何一处。同一个页面里，快照直连、服务列表经控制面，看起来像不一致，其实是
   没人定过规则。
2. **没有兜底。** 一个动词如果被误标成只读，没有任何东西会拦住它。
3. **PR #76 的实测**（`docs/plans/host-ops-channel-audit-2026-11-17.md`）显示：host-ops
   的所有只读动词在 Agent 侧已经压到 **1 毫秒以内**（除进程列表与错误日志）。也就是说
   「走哪条通道」对 Agent 侧的耗时影响已经可以忽略——**这条规则的价值现在是治理，
   不是性能**。这个定位必须写清楚，否则会有人以为分类是为了提速。

## 决策

### 1. 只有三个类别

| 类别 | 含义 | 允许的通道 |
|---|---|---|
| `observe` | 周期性观测数据（指标、失败单元、Peer 握手、端口占用） | 优先直连，不通时经控制面 |
| `ops-read` | 只读的运维查询（服务列表、进程、防火墙规则、定时任务） | 优先直连，不通时经控制面 |
| `control` | 一切改变状态的操作、含机密的数据、跨节点汇总 | **只经控制面，永不直连** |

### 2. 进入前两类的四个条件（必须同时满足）

1. 只读，不改变节点状态；
2. 不含私钥、密码、令牌这类拿到就能直接使用的秘密；
3. 不依赖跨节点汇总，也不需要 D1（配置库）里的数据；
4. 直连失败时能改由控制面转发，且**结果完全一样**。

> 第 4 条是硬条件：如果某个数据直连和控制面的结果会因为时序不同而不一致，
> 它就不能进前两类。否则通道降级会变成一个偶发的、难复现的 bug 来源。

### 3. 明确排除的两类数据（虽然它们「只读」）

| 数据 | 为什么不 |
|---|---|
| **SSH 公钥清单**（`keys.list`） | 它是「谁能登进这台机器」的完整清单，属侦察目标；且与 `keys.add`/`keys.remove` 是同一份数据，读写分走两条通道会让「刚加的 key 没出现在列表里」这类竞态更难排查 |
| **服务日志**（`svc.logs`）与**错误日志**（`logs.errors`） | 日志内容不可控，令牌泄漏最常见的途径就是日志。即使做了脱敏，也不该让日志出现在直连通路上 |

这两条是与 PR #75 提案的明确分歧：提案把 `keys.list`、`svc.logs` 列进了 `ops-read`，
本 ADR **不采纳**。理由：通道规则要能放心地用很久，为 5 个动词快 0.5ms 而把
「登录权限清单」和「日志内容」放进直连，是不划算的交换；它们本来也不是高频操作。

### 4. 类别是动词注册表的一个字段，是唯一权威

- **host-ops**（本次覆盖）：类别写在 `khc_host.py` 的 `CHANNELS` 里，与
  `PUBLIC_VERBS`/`WRITE_VERBS` 同源派生校验；`channel_map()` 在缺项、写动词标只读、
  未知类别三种情况下启动即抛错。
- 导出到 `packages/contracts`（`HOST_OPS_CHANNELS` + `hostOpsChannel()`），
  前端与 Worker 都从这里读。两份声明靠 `packages/contracts/test/channel.test.ts`
  读 Python 源做一致性校验，漂移时测试失败。
- **其他适配器（wireguard / caddy-site）本次不加 `channel` 字段。** 理由：它们目前
  没有任何直连通路（直连只存在于观测快照与将来的 C2），给 19 个动作补一个当前无人
  读取的字段是空转。等某个适配器真的要开直连时再补，那时字段才有意义。
  **这条是刻意的范围限制，不是遗漏。**

**host-ops 新增动词不填类别就注册不了。** 单测直接失败。

### 5. 三道兜底

1. **字段必填**（host-ops）：缺类别时 `channel_map()` 抛 `ValueError`，启动即失败。
2. **写动词不得标只读**：`WRITE_VERBS`（以及各适配器 `write: True` 的动作）如果被标成
   `observe` 或 `ops-read`，单测失败。
3. **Agent 侧二次校验**：观测服务收到 `control` 类别的请求一律拒绝。即使票据被伪造，
   也拿不到 `control` 类数据的直连通道——因为 `control` 不签发对应的票据作用域。

### 6. 前端不写任何通道判断

统一一个取数函数（`readNode(hubId, verb, params)`），由它按类别选通道并负责降级。
写操作仍走现有 `host-ops/call`。**页面里不允许出现「这个功能走还是不走直连」的判断。**

### 7. Peer 数据的边界

Peer 的数据链路是 `浏览器 → 控制面 → Hub Agent → SSH → Peer`。
**浏览器无法直连 Peer**，类别规则对它不适用：带 `target=Peer` 的请求一律经控制面，
与类别无关。

这一点必须写进规则，否则会有人给 Step 2 之外的动词也加上直连，然后在 Peer 上失败。

## 后果

**好处**
- 新增动词时有明确依据，不再靠个人判断；
- 误标只读会被测试拦住；
- 用户只需要理解一个状态（节点栏的「实时 · 直连 / 实时 · 经控制面」），不需要理解三个类别。

**代价**
- host-ops 的动词表加了 `CHANNELS`（动到冻结核心，见 `AGENTS.md` §5 的例外流程）；
- 两份声明（Python 与 contracts）要维持一致，靠一个读源码的测试兜住；
- 规则本身不会提速。**提速是 C2 的事，而 C2 是否值得做取决于「Worker→Hub 那一跳」的实测**
  （PR #76 §5.2）。

## 没做什么

- 不含 C2（`/_live/ops` 直连端点）。C2 需要先测出 Worker→Hub 那一跳的耗时。
- 不改 `WRITE_VERBS` 的现有内容。
- 不动 `keys.list` / `svc.logs` 目前的通道（它们本来就走控制面，本 ADR 只是把
  「以后也不许迁」写成规则）。
