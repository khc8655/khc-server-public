# ADR-0017: 对外服务可见性（站点表「后端」列 → 「对外服务」页）

- 状态：已接受（主人 2026-11-12 拍板：先 C 后 A；只读聚合，不新增数据模型）
- 日期：2026-11-12
- 决策者：主人
- 关联：`docs/plans/ui-ia-redesign-2026-11-12.md` §4、§5、`docs/ui-redesign/page-specs.md`、`agent/adapters/caddy_site.py`、`agent/adapters/wireguard.py`、`agent/adapters/port_forward.py`

## 背景

主人明确：WireGuard 用于连接没有公网地址的 VM，把 VM 上的程序发布出来；端口转发用于把这类 VM 的 SSH、远程桌面转发出来；程序目前手动安装，再由 Caddy 发布。
现有界面按模块组织（站点 / 内网穿透），看不出“对外提供了什么、后端在哪、通不通”，内网 VM 只能看到裸地址，VM 掉线时看不出原因是 Peer 离线。

## 选项

| 选项 | 做法 | 利 | 弊 |
|---|---|---|---|
| A「对外服务」页 | 新路由 `/hubs/:id/services`，聚合网页服务与远程访问 | 一页看全 | 新增路由/侧栏/空态/390 改动面 |
| B 新增“服务”数据模型 | D1 新表或新适配器记录引用关系 | 引用明确 | 违反核心冻结，双写一致性、迁移成本 |
| **C 站点表「后端」列（先做）** | 站点表新增「后端」列，按地址识别本机 / 内网 VM（带 Peer 在线）/ 内网未登记 / 外部 | 改动最小、零后端改动、零新增请求 | 远程访问仍分散 |
| **A+C 组合（采用）** | 先做 C 验证推导规则，再在同一个 `services.ts` 上做 A | 风险分两批；推导单一来源 | 两批工作量，但可独立回滚 |

## 决策

采用 **先 C 后 A**：
1. 「对外服务」是**视图**，不是数据；不新增 D1 表、不改写入链路、不新增请求。
2. 第 3 批：站点表新增「后端」列，识别规则写在 `apps/web/src/data/services.ts`，全分支单测。
3. 第 4 批：新增 `/hubs/:id/services` 页，网页服务 = `caddy-site` 的 `kind=proxy` 站点，远程访问 = `port-forward` 规则；后端识别与状态推导复用同一 `services.ts`。
4. 写操作只走现有站点、转发的保存 + apply 链路；行点击开既有抽屉，不新增第二种详情/操作入口。页头入口沿用术语表既有说法：[新增站点] / [新增转发]。
5. 未生效必须在状态列右侧直接给 [生效]（既有 apply 动作，按 L2 确认），不得收进 `⋯`；行内按钮仍 ≤2。
6. 术语统一为「对外服务」（网页服务 / 远程访问 / 后端），不与既有「扩展应用」混用。
7. 托管安装不在本 ADR 范围内。

## 影响 / 迁移 / 回滚

- 第 3 批：站点表新增一列，窄屏按 `low priority` 隐藏；回滚 = 去掉列与纯函数。
- 第 4 批：新增路由与侧栏项，`page-specs.md` 登记为类型 B；回滚 = 移除路由与侧栏项，抽屉组件改动可保留。

## 验证

- `services.test.ts` 覆盖识别与状态推导全部分支（含 IPv6、带 scheme 上游、多上游、Peer 停用、WireGuard 未安装时 10.x 归「外部」）。
- staging：发布一个本机程序（`127.0.0.1`）和一个 VM 程序（经 Peer），停掉 VM 的 WireGuard，确认「后端」与状态正确；390 无横向滚动。
