| 项 | 改前 | 改后 |
|---|---|---|

## 2. 改了什么

### 2.1 采样窗口 500ms → 100ms

`PROCESS_CPU_SAMPLE_INTERVAL = 0.1`。

这个等待不是为了「慢」，是为了测准 CPU%：进程 CPU 要两次采样求差，窗口太短
jiffies 增量可能为 0。100ms 在 `SC_CLK_TCK=100` 下约 10 个 tick，够用（实测仍能
把跑满单核的进程测成 105.8%）。

### 2.2 分母改用真实经过时间（关键）

原实现：`span = _clock_ticks() * PROCESS_CPU_SAMPLE_INTERVAL`

**问题**：`time.sleep(0.1)` 只保证「至少睡 0.1 秒」，实际可能 overshoot 到 0.13 秒。
窗口 500ms 时 overshoot 占比小、可忽略；缩到 100ms 后，同样的 overshoot 会让
CPU% 系统性偏高（分母偏小 → 结果偏大）。

改为用两次采样之间的 `MONOTONIC()` 真实差值做分母。`MONOTONIC` 做成可注入
（与 `SLEEP` 同款），测试才能控制它。

### 2.3 窗口过小的退化保护

分母接近 0 会算出荒谬数值（改的过程中实测过 **2279%**）。加 `MIN_CPU_SAMPLE_WINDOW = 0.001`：
低于 1ms 认为采样无效，返回空（各进程 CPU 报 0），**不报假数**。

### 2.4 `snapshot` 里省掉重复的 200ms（本次第二大收获）

`status_verb` 原本在拿不到 CPU 基线时会自己 `sleep(0.2)` 再采一次。
但面板走的 `snapshot{processes:true}` 里，`collect_processes` 本来就要睡 100ms ——
**两段等待串起来就是 300ms**。

改成：需要进程时，**先采进程**（它睡觉的 100ms 正好让 `/proc/stat` 累积出增量），
之后再取 `status`，就不必再等自己的 200ms。

> 顺序不能反。先 `status` 再采进程的话，`status` 那一刻还没有任何时间流逝，
> CPU% 会是 `null` —— 这是静默退化，已用测试锁住（`test_processes_sampled_before_status`）。

### 3.2 CPU% 准确性未退化

关键是**它被正确排到第一位**，S0 提到的 GitHub #35（刚启动就跑满的进程被挤出列表）
没有回退。

### 3.3 端到端

```

snapshot 无进程:     385-423 ms（首次，含模块加载）

```

## 4. 一个没解决的发现（下一批再处理）

`version` 这个**什么都不做的动词**经 HTTP 调用要 124–198 ms，而：
- `/health` 只要 0.6 ms（同一 HTTP 服务，说明网络与框架无问题）
- `main("version")` 在进程内只要 0.1 ms
- 模块首次加载：独立进程 45.9 ms / 同进程 87.8 ms

即：**`host-ops` 这条路径上有约 78 ms 的固定开销，没定位到**。
已排除：TLS（8443 是明文 HTTP）、审计写盘（内核里没有）、写锁（`version` 是只读）、
适配器重复实例化（内核缓存）、模块重复加载（有 `_script_module` 缓存）。

它不影响本次成果（进程采样已从 498ms 等待降到 100ms），但它是**每个 host-ops 调用
都要付的固定税**，比进程采样更值得优化。建议下一批单独排查：
在 `handle_action` 入口/出口打点，看时间落在内核、适配器 dispatch 还是 HTTP 编解码。

> 这也是为什么端到端是 280–305 ms 而模块直调只有 134 ms ——
> 差值 ≈ 78 ms 固定开销 + 100 ms 采样窗口。

## 6. 没做什么

- **没加缓存**：面板只在打开进程段和切换排序时调用，没有轮询。加缓存会让 CPU% 陈旧，
  与「实时监控」的预期不符，收益也不大（本来就只是单次等待）。
- **没改用 `ps` 的 `%cpu`**：那是进程生命周期均值，会让刚启动就跑满的进程排不进列表
  （GitHub #35 修过的问题），属于回退。
- **没动通道**：S0 已证明传输只占 85–100 ms，动它解决不了大头。
