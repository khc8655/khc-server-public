# S0 浏览器直连通道实测（2026-11-16）

> 状态：证据（一次性验收记录，写完不再修改） ｜ 最后核验：2026-11-16
> 面板 0.17.2 / Agent 0.5.1 ｜ 节点 oracle-x86-2（新加坡，域名 `oracle-x86-2.khc6.dpdns.org`）
> 关联：PR #75 提案 §8

## ⚠️ 先说这轮测不了什么

**我这条网络到新加坡太差，不足以作为 C2 的判据。** 实测中位 1661ms、P90 2107ms、
抖动到 11.8 秒。在这种链路上比较「150ms 的通道差」没有意义。

提案 §8 要求在「主人常用的网络下（家里宽带、手机热点各测一轮）」测 —— 那必须由主人在
真实使用环境里跑。本文只给**能确定的结构性结论**和**测量方法上的修正**。

## 1. 一个提案没考虑到的结构问题

提案 §8 说「两条路现在都已经存在，可以直接对比」：

- 直连：`GET https://<domain>/_live/snapshot?ticket=…`
- 经 Worker：`GET /api/v1/nodes/:id/snapshot`

**但两条路走的是同一个域名、同一个 Caddy、同一次 TLS 握手。** 真正的差别只有
「Caddy 之后是直接给 Agent 还是绕一趟 Worker」。而这轮实测发现：**Caddy 这一层的开销，
比 Worker 那一跳大得多。**

### 1.1 实测（Hub 本机，排除公网）

| 路径 | 耗时 |
|---|---|
| 直连 Agent `127.0.0.1:8443` | **0.4 ms** |
| 直连 Caddy 的 upstream | 0.4 ms |
| **经 Caddy（HTTPS + 域名）** | **24–74 ms** |

### 1.2 从本机经公网

| 路径 | 中位 | P90 | max |
|---|---|---|---|
| `http://140.245.108.105:8443/health`（绕过 Caddy/TLS） | **243 ms** | 1222 ms | 2190 ms |
| `https://oracle-x86-2.khc6.dpdns.org/health`（经 Caddy+TLS） | **1661 ms** | 2107 ms | 2798 ms |

TLS 各阶段拆解（一次典型请求）：

```
dns=0.06ms  connect=0.2ms  tls=817ms  total=1356ms
plain-http 直连 IP: 279ms
```

**慢在 TLS 握手（约 800ms）和 Caddy 处理，不在网络传输（0.2ms 建连）。**

### 1.3 这对 C2 意味着什么

C2 的假设是「直连比经 Worker 快 150ms 以上」。但如果两条路都过 Caddy + TLS：

- 直连省下的是 **Caddy → Worker → Agent** 这一跳
- 这一跳在 Hub 本机只有 **几毫秒到几十毫秒**（Worker 是 Cloudflare，还要多一次公网往返）

所以要省到 150ms，靠的不是「直连」，而是「**Worker 那一趟公网往返**」。
**如果 Worker 和 Caddy 在同一个边缘/机房，这 150ms 根本不存在。**

> **需要先在提案里补一条前提**：直连的收益 = `浏览器→Worker→Agent` 减去
> `浏览器→Caddy→Agent`。这个差值取决于 Worker 部署在哪、和 Caddy 之间隔多远。
> 在测清楚这个之前，「直连更快」不是先验成立的。

## 2. 测量方法的三个修正

### 2.1 必须固定连接复用状态

TLS 握手 817ms 会完全淹没通道差异。浏览器有 keep-alive，第一次打开页面要付握手，
之后的请求不用。所以：

- 第一轮测「冷连接」，只用来量化首次打开的成本
- 主体测量必须**复用连接**，否则测的是握手不是通道

### 2.2 不能用 `/health` 当基线

`/health` 在鉴权之前就返回，走的代码路径和 `host-ops` 完全不同（S0 早期已经踩过这个坑：
`/health` 0.4ms，`host-ops` 190ms）。

要扣通道开销，基线应该是「一个**什么都不做但要完整走鉴权与路由**的动词」——
现在正好有：`version`，Agent 侧只要 2ms（#72 之后）。

### 2.3 提案里的 `version` 基线已经过时

提案写的时候 `version` 是 190ms，现在 2.5ms。这意味着：

- 用 `version` 经 Worker 测出的耗时，现在**几乎全是通道开销**，可以直接当基线用
- 反过来说，**Agent 侧已经不可能再贡献可优化的时间了** —— 用户感到的慢，100% 在通道上

## 3. 能确定的结论

1. **Agent 侧已经没有优化空间**：`version` 2.5ms、`svc.list` 8ms、`fw.show` 11ms。
   要继续降只能动通道。
2. **Caddy + TLS 是当前最大的单项开销**（本地 24–74ms，公网 TLS 握手 800ms）。
   它比 Worker 那一跳更值得关注，而提案没有提到它。
3. **我这条网络不能作为判据**。需要在主人的常用网络下重测。
4. **配额问题独立成立**：主机运维页一次打开要发 5–7 个请求（提案 §2.3），
   这与通道快慢无关，C2 能减少 5–7 次 Worker 调用。

## 4. 建议：S0 应该怎么重做

在主人家宽 + 手机热点各跑一轮，每轮：

```
1. 冷连接测 3 次（首次打开成本，含 TLS）
2. 复用连接测 20 次，交替请求，记录 performance.now()
   a. GET  https://<domain>/_live/snapshot?ticket=<有效票>       ← 直连
   b. GET  /api/v1/nodes/<id>/snapshot                            ← 经 Worker
   c. POST /api/v1/nodes/<id>/apps/host-ops/call  {verb:version}  ← 通道基线
3. 记录打开一次主机运维页的 Worker 请求数（Network 面板）
```

判据不变（差 150ms 以上才做 C2），但要**同时记录「Worker 与 Caddy 是否同机房」**，
否则差值的来源无从解释。

## 5. 这轮没做的

- 没有在浏览器里实测（需要一个已登录的会话拿 `snap` 票据；这一步交给主人在真实环境做）
- 没有测不同地理位置（只在我的网络下）
- 没有测配额消耗的实际数字（要看 Cloudflare 后台）
