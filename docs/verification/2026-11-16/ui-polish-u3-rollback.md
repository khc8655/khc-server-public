# U3 前置：Peer 网络与回滚鲁棒性实测（2026-11-16）

> 状态：证据（一次性验收记录，写完不再修改） ｜ 最后核验：2026-11-16 ｜ 关联：提案 `docs/plans/ui-polish-2026-11-16.md` §6、`ui-polish-s0.md` §③
> 节点：`oracle-x86-2`，netns 内真实 WireGuard（kernel 7.0.0-1016-oracle，wg 工具 `/usr/bin/wg`）

## 0. 先纠正一处此前的误读

S0 的 §③ 结论「公网 SSH 会断」是在**只测了「全部流量走 Hub」这一个可选项**的前提下得出的，
当时没有说清提案的主设计。重读提案 §6，原始设计是：

- 新 Peer **默认只能和 Hub 通**；
- 出网方式**默认「仅内网流量走 Hub」**——Peer 自己的公网网络保持原样；
- 只有面板上配的应用转发 / 端口转发业务走 wg；
- 「全部流量走 Hub」是**用户显式选择的可选项**，选中必须二次确认。

也就是说：**S0 的风险只在用户主动勾选那个可选项时出现，不影响默认状态。**
提案在这点上是正确的，此前我在回复里把它当成默认方案来批，是误读。

本文件只针对那个可选项，回答两件事：**断开的确切原因**、**回滚是否真的稳健**。

## 1. 断开的确切原因：endpoint 自环

### 1.1 拓扑

用三个 netns 复刻真实跨网段结构（Peer 与 Hub 不在同一 /24，必须走默认路由，
这样才可能被 `0.0.0.0/0` 劫持）：

```
Peer peerns  公网 172.50.0.20 ──┐
                                ├─ 路由 rtrns 172.50.0.1 / 172.60.0.1
Hub  hubns   公网 172.60.0.10 ──┘

Peer wg0 10.77.0.2 ── WireGuard ── Hub wg0 10.77.0.1（Hub listen 51999）
```

### 1.2 实测

加载 `AllowedIPs = 0.0.0.0/0`（三步：`table 51820` 默认路由、
`ip rule not fwmark`、`ip rule table main suppress_prefixlength 0`）之后：

```
到 Hub endpoint 172.60.0.10:  172.60.0.10 dev wg0 table 51820 src 10.77.0.2
Peer -> Hub(wg 10.77.0.1):   0 received / 100% packet loss
```

**加载全量路由后，Peer 连 Hub 都不通了 —— 不只是公网 SSH 断，隧道本身也死。**

### 1.3 原因

WireGuard 的隧道包要发往对端 endpoint（Hub 的公网 IP `172.60.0.10`）。
但这条地址现在被 `table 51820` 的默认路由接管，指向 **wg0 自己**。
于是封装包被投回 wg0 → **自环**，永远出不了物理网卡。

这跟 S0 里「保留 endpoint /32 能防自环」是同一件事，但 S0 当时**没有验证自环是否真的发生**。
本次实测确认：**不加那条 /32，隧道必死。**

### 1.4 修法（wg-quick 本来就会做，但我们的客户端配置可能漏了）

```
ip route add 172.60.0.10/32 via 172.50.0.1 dev vpeer
```

加上之后：

```
到 Hub endpoint:  172.60.0.10 via 172.50.0.1 dev vpeer src 172.50.0.20   ✓ 不打环
Peer -> Hub(wg):  2 received                                            ✓ 隧道恢复
Peer -> 1.1.1.1:  dev wg0 table 51820                                   ✓ 仍走隧道
```

**对 U3 的硬要求：客户端配置生成「全部流量走 Hub」时，必须先写好 endpoint 的 /32 直连路由，
再装默认路由。顺序错了就是当场失联。** `wg-quick` 自己处理这个，
但面板若用 `wg set` + 手写路由（`docs/live-observation.md` 之外的路径），必须自己保证顺序。

## 2. 回滚鲁棒性（四项实测）

| 场景 | 做法 | 结果 |
|---|---|---|
| R1 基线 | 默认只放行 wg 网段 | Peer→Hub(wg) `2 received`；Peer→公网走 `vpeer` 物理网卡，**不经隧道** —— 与提案默认值一致 |
| R2 加载全量 | 装 `0.0.0.0/0` | Peer→公网走 `wg0 table 51820`；**Peer→Hub(wg) 100% 丢包**（endpoint 自环，见 §1） |
| R3 隧道断开 + Peer 侧定时器 | 删 Hub wg0 造成彻底失联，再等 5s 定时回滚 | 回滚后默认路由恢复 `via 172.50.0.1 dev vpeer`，`ip rule` 残留 **0** 条 —— **失联状态下仍自愈成功** |
| R4 Hub 侧主动撤销 | 重建 Hub wg0、把 Peer 的 AllowedIPs 收回 `/32` 并重载 | Hub 侧重载成功后 Peer→Hub(wg) `1 received` 恢复 |

### 2.1 R3 为什么能成功（重要）

定时器只操作**本机路由表**（`ip rule del` / `ip route flush`），不依赖任何网络。
所以即使 Peer 已经完全失联（隧道断、公网也因默认路由被劫持而不通），
只要定时器还在跑，它就一定能把路由恢复。

**结论：Peer 侧定时回滚是可靠的，前提是定时器真的被布防了。**

### 2.2 R3 的边界（必须写进设计）

R3 成立的前提有三个，缺一不可：

1. **定时器必须在加载路由之前布防**。顺序反了（先加载再布防），中途失联就没机会布防。
2. **Peer 的 cron / systemd 必须可用**。如果 Peer 是精简系统没有 systemd，这条路不存在。
3. **定时器不能被防火墙规则误杀**。`fw.*` 只动 `inet khc_fw`，理论上不影响 systemd；
   但若用户在别的路径上动了 OUTPUT 链，定时器照样跑（它是本地进程，不出网）。

### 2.3 R4 作为第二道防线

R4 证明：**Hub 侧能独立撤销，不依赖 Peer 的出网能力**。
Hub 改 `AllowedIPs` + `wg syncconf` / 重载后，Peer 的握手会重新建立
（Peer 有 `persistent-keepalive 5`，会自己重连）。

> 注意：R4 的实际效果依赖 Peer 有 keepalive 且 Peer 自己还没关机。
> 如果 Peer 因为路由错误导致 keepalive 包也发不出去（见 §1 自环），
> Hub 侧改配置**不会**让 Peer 的路由表自动恢复 —— Peer 的 `ip rule` / 路由还在错误状态。
> 所以 R4 不是 R3 的替代品，而是「R3 失效时保证 Hub 侧侧数据一致」的补充。

## 3. 对 U3 的设计约束（结论）

### 3.1 默认状态（提案原文，保持）

新 Peer 默认只能和 Hub 通；出网方式默认「仅内网流量走 Hub」。
面板上配的应用转发 / 端口转发业务走 wg，**Peer 原有公网网络不动**。
这一层没有任何风险，S0 与本次实测都没有发现副作用（见 `ui-polish-s0.md` §④）。

### 3.2 「全部流量走 Hub」的四条硬要求

1. **默认关闭、按 Peer 单独开启**，不做「一键全部切换」。
2. **先写 endpoint /32，再装默认路由**。顺序反了当场自环失联（§1.4）。
3. **二次确认框必须写确定语气**：
   - 「这台 VM 的公网 SSH 会立即断开」（不是「可能」）；
   - 「开启后如果隧道出问题，这台 VM 会完全失联」；
   - 「全部流量计入 Hub 带宽」；
   - 「DNS 需另外配置」。
4. **回滚必须双层**：
   - 第一层：Peer 侧定时器（R3 已验证可靠）。**必须在加载路由之前布防**，
     且布防失败时**中止操作**，不要带着错误配置继续。
   - 第二层：Hub 侧可独立撤销（R4），用于保证 Hub 侧配置不残留。

### 3.3 仍未验证（需要真机）

- **真实发行版上的 systemd-run 定时器**（netns 里跑不了 systemd，本次用 `sleep` 代替）。
  必须在带 systemd 的真机上再验一次「布防 → 失联 → 自愈」。
- **DNS**：加载 `0.0.0.0/0` 后解析行为。提案说「需要另外配置」，本次未测。
- **IPv6**：若只接管 IPv4、保留 IPv6 默认路由，SSH 走 IPv6 是否不断。
  需要一台 IPv6 可达的 Peer；现有 Peer 的 IPv6 从外部测不通，无法验证。

## 4. 清理

所有 netns（`hubns` / `peerns` / `rtrns`）、veth（`vr1` / `vr2`）、临时密钥（`/tmp/rb_*.key`）
均在脚本 trap 中清理；复核 `ip netns list` 为空。
