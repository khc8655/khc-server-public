# C2 门槛判定：Worker→Hub 那一跳只有 3ms，不做 C2（2026-11-17）

> 状态：证据 + 决策依据｜最后核验：2026-11-17
> 面板 0.17.3 / Agent 0.5.2 ｜ 关联：PR #75 §8、PR #76 §5.2、ADR-0020

## 1. 结论

**C2 不做。** 门槛是「Worker→Hub 那一跳超过 150ms」，实测只有 **2.8–3.3 ms**，
差了两个数量级。

这不是「接近门槛、可以勉强做」，而是**根本没有空间**：C2 能让只读运维省下的上限，
就是这一跳的全部耗时，也就是 3ms。

## 2. 关键测量

### 2.1 Cloudflare 在新加坡有边缘节点

```
Hub 上执行：curl https://1.1.1.1/cdn-cgi/trace
colo=SIN
loc=SG
```

**Hub（新加坡）和 Cloudflare 边缘在同一个城市。** 这是这次测量最重要的前提
——也是最容易被忽略的：Worker 不是「在美国某个机房」，而是就近部署在 CF 边缘。
Hub 在新加坡，CF 在 SIN 有节点，两者之间几乎没有距离。

### 2.2 那一跳的真实耗时

| 测什么 | 结果 |
|---|---|
| Hub → CF 边缘 TCP 建连 | **1.2 ms** |
| Hub → CF 边缘 完整往返（首次，含 TLS） | 31 ms |
| **Hub → CF 边缘 完整往返（复用连接）** | **2.8–3.3 ms** |

### 2.3 对照：用户那一段才是慢的

| 路径 | 耗时 |
|---|---|
| 我（本机）→ CF 边缘 | 197–217 ms |
| 我（本机）→ Hub 直连 | 176–230 ms |
| **Hub → CF 边缘** | **3 ms** |

用户到 CF、用户到 Hub 都在 200ms 量级，而 Hub 到 CF 只有 3ms。

### 2.4 链路全景

```
用户 ──[约 200ms]──> CF 边缘 ──[3ms]──> Worker 逻辑 ──[3ms]──> Hub Agent ──[<1ms]──> 数据
用户 ──[约 200ms]──> Caddy ──[24-74ms]──> Hub Agent ──[<1ms]──> 数据（直连方案）
```

**两边的差别：**
- 经 Worker：200 + 3 + 3 = **约 206 ms**
- 直连：200 + 24~74 = **约 224–274 ms**

**直连反而更慢**，因为 Caddy 的处理（24–74ms）比 Worker 那一跳（3ms）更贵。

## 3. 为什么和提案的预期差这么远

提案（PR #75 §2.2）的判断是「Agent 侧已压到个位数毫秒，用户感受到的慢，
大概率就落在『浏览器→Worker→Agent』这一段的公网往返」。

**这个推断在当时是合理的，但前提错了**：它假设 Worker 和 Hub 之间有一段真实的公网往返。
实际是 Cloudflare 把边缘节点放在了 Hub 同城，所以那一段几乎不存在。

真正花时间的是：
1. **用户到最近边缘点的那 200ms** —— 两条路都要付，谁也没有优势；
2. **Caddy 的处理 24–74ms** —— 只有直连要付，比 Worker 那一跳更贵。

> **这条要记进 ADR**：判断「直连是否更快」不能只看架构图上的跳数，
> 要看 Cloudflare 边缘和 Agent 的地理关系。CF 在同城时，Worker 那一跳是免费的。

## 4. 那 C2 该换成做什么

按实测收益排序：

| 优先级 | 做什么 | 依据 | 预期收益 | 状态 |
|---|---|---|---|---|
| 1 | **关掉 Agent 的 Nagle** | 每请求都付 40ms | 每请求 40ms | ✅ **已修（Agent 0.5.3）** |
| 2 | 首次 TLS 握手 23–46ms | 只在首次付 | 首次 20–40ms | 待评估 |
| 3 | 减少段切换的重复请求 | 已确认没有可省（PR #78 §4.2） | 0 | — |
| — | ~~C2 直连只读运维~~ | 收益上限 3ms | **0–3ms** | **不做** |

**第 1 项是这一整轮排查里最大的收益**，而且它是「每请求都付」的 —— 比 C2 的
「只对 7 个只读动词生效、上限 3ms」高两个数量级。

**第 1 项最值得做**：`Caddy 24–74ms` 是每个请求都要付的，而 Worker 那一跳只有 3ms。
换句话说，**当前架构里 Caddy 是比 Worker 更该被质疑的一层。**

### 4.1 Caddy 的 24–74ms 已经查清并修好——但根因不在 Caddy

继续排查时发现：**直连 Agent（不过 Caddy）在同一连接上第 2 个请求也要 40ms。**
所以问题不在 Caddy，在 Agent 的 HTTP 服务端。

**根因：`BaseHTTPRequestHandler` 默认启用 Nagle 算法。** 配合 HTTP/1.1 keep-alive，
响应头与响应体分两次写，第二段被 Nagle 按住等 ACK，而客户端的 ACK 被延迟确认
拖了约 40ms —— 就是经典的「延迟 ACK」现象。

**修复：给 Handler 加 `disable_nagle_algorithm = True`。** Agent 0.5.3。

实测对比（同一连接连续请求）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 直连 Agent 第 2 次起 | **40.9 ms** | **0.16–0.24 ms** |
| 经 Caddy HTTPS 第 2 次起 | **41 ms** | **0.46–0.52 ms** |
| 业务请求 `version` 第 2 次 | 40+ ms | **0.35 ms** |

**约 80–250 倍。** 这是本轮最大的一笔收益，而且和 C2 完全无关 ——
它是所有 keep-alive 请求都在付的固定税。

> **为什么之前一直没发现**：新建连接只要 0.4ms，所以单次 `curl` 测不出来。
> 一旦连接复用（浏览器、Caddy 到 upstream、任何 HTTP 客户端都会复用），
> 第 2 个请求起就固定多 40ms。前面 PR #76 里那些「0.5–0.8ms」的稳态数据，
> 其实是修复前恰好在新连接上测的。

## 5. 一个副产品：这个测量方法可复用

以后判断「要不要为某条数据开直连」，只需三步：

```bash
# 1. Agent 上确认 CF 边缘是否同城（colo 就是 IATA 代码）
ssh <hub> 'curl -s https://1.1.1.1/cdn-cgi/trace | grep colo'

# 2. 量那一跳（复用连接，否则测的是 TLS）
ssh <hub> 'curl -s -o /dev/null -w "%{time_total}" https://<worker>/
             --next -s -o /dev/null -w "%{time_total}" https://<worker>/'

# 3. 和 150ms 门槛比
```

如果 `colo` 和 Agent 同城，那一跳基本可以视为免费，不需要再测第二步。

## 6. 状态

- C2 **不做**，ADR-0020 的规则保留（该写的规则已经写了）；
- 提案 PR #75 的第 3 问「只读运维先测后定吗」——**已定：测了，不达标，不做**；
- 新的优先项：查 Caddy 的 24–74ms（建议作为下一批）。
