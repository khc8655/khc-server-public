# 主机运维通道梳理：哪些走直连、哪些必须经控制面（2026-11-17）

> 状态：梳理（供通道分类提案 C1 使用）｜ 最后核验：2026-11-17
> 面板 0.17.2 / Agent 0.5.1 ｜ 逐项核实自代码，非推测
> 关联：PR #75、`docs/verification/2026-11-16/channel-s0.md`

## 0. 一句话结论

**主机运维目前一条直连都没有。** 18 个动词全部经 Worker（`POST /apps/host-ops/call`），
和节点有没有 HTTPS 域名无关。唯一会直连的是顶部的 10 秒指标快照，它不属于主机运维。

所以「主机运维的直连梳理」实际是**决定要不要新增直连**，而不是梳理现有直连——
这与提案 C2 的范围一致，但判断依据需要比提案写得更细。

### 1.1 直连的判定条件（比提案写的更严）

`snapshot.ts:594` 的 `isHttpsEndpoint()` 只认 `https:` 协议。这意味着：

- 有 HTTPS 域名 → 直连
- 只有 http / 只有 IP / URL 非法 → **一律走控制面**（避免混合内容与证书失败）

这个判定已经覆盖了提案 §4 的「只有 HTTP 的地址」情形，**不需要额外处理**。

## 2. 18 个动词的完整分类建议

### 2.1 可以直连（`ops-read`）——7 个

前提：只读、不含可直接使用的秘密、不依赖跨节点汇总。

| 动词 | Agent 侧耗时（稳态） | 内容 | 判断 |
|---|---|---|---|
| `version` | **0.6 ms** | 版本号 | 无敏感性 |
| `status` | **0.6 ms** | 主机名、负载、uptime | 无敏感性 |
| `svc.list` | **0.8 ms** | systemd 单元 | 无敏感性 |
| `fw.show` | **0.7 ms** | nftables 规则 | 规则本身是运维信息，不含密钥 |
| `cron.list` | **0.5 ms** | cron 条目 | 无敏感性 |
| `keys.list` | **0.6 ms** | SSH 公钥清单 | 见 §2.2，建议不直连 |
| `logs.errors` | **66–72 ms** | 近 24h 错误（已脱敏） | 跑 journalctl，见下 |
| `svc.logs` | **0.7 ms** | 单个服务日志 | 见 §2.2，建议不直连 |
| `processes` | **120–190 ms** | 进程列表 | 100ms 是 CPU 采样窗口，省不掉 |

> **11-17 复测修正**：早先记的 2–11 ms 是**带着 `curl` 进程启动开销**测的（每次调用起一个
> curl，约 2–8ms 固定成本）。改用连接复用后，除 `processes` 和 `logs.errors`，
> **所有只读动词都在 1 毫秒以内**。这个量级意味着：走哪条通道，Agent 侧都不是瓶颈。

### 2.2 建议不直连——2 个（提案把它们算进了 `ops-read`）

| 动词 | 为什么不 |
|---|---|
| `keys.list` | 返回**完整公钥内容**，等于「谁能登进这台机器」的全清单。公钥本身不算秘密，但这份清单是攻击者的侦察目标。而且它和 `keys.add`/`keys.remove` 是同一份数据，读写分开走两条通道会让「刚加的 key 没出现在列表里」这种竞态更难排查 |
| `svc.logs` | 日志内容不可控。即使做了脱敏，服务日志里出现密钥/令牌是最常见的泄露途径。**日志类数据不应该出现在直连通路上** |

> 这两个是我与提案的不同意见。提案 §3.1 把 `keys.list`、`svc.logs` 都列进了 `ops-read`。

### 2.3 必须经控制面（`control`）——9 个

8 个写动词 + `snapshot`：

- `fw.apply` / `fw.confirm` / `keys.add` / `keys.remove` / `svc.restart` /
  `svc.reset-failed` / `cron.set` / `cleanup` —— 改变节点状态
- `snapshot` —— 它是 `status + processes` 的合并包，含进程列表。功能上可以直连，
  但**前端只在进程抽屉里用它**，而抽屉里还有「结束进程」这类写操作入口。
  为一致性保留在控制面（这条可以再议）

## 3. 一条提案没写明的边界：Peer 的数据无法直连

前端调用形如 `callHostOps(hubId, target, verb)`，`target` 可以是 `self` 或 Peer 名。

- `self` → 浏览器 → 控制面 → Hub Agent → 进程内执行
- Peer → 浏览器 → 控制面 → Hub Agent → **SSH** → Peer 执行

**Peer 的数据必须经 Hub 中转，浏览器直连不了。** 即使 C2 做了 `/_live/ops`，
也只覆盖 `target=self`。而主机运维页的 Peer 面板（`PeerOpsPanel.tsx:144`）用的正是
`target=peer.name`。

> **这是 C2 收益要打折的地方**：提案 §7 说「C2 只是把浏览器到 Hub 这一段改为直连」，
> 但没说清 Peer 完全不在覆盖范围内。多节点用户感受不到提速。

## 4. 一次打开的请求数（配额依据）

| 场景 | Worker 请求数 |
|---|---|
| 打开主机运维页（默认服务段） | 2（页面初始化）+ 1（`svc.list`）+ 10 秒快照轮询 |
| 切到进程段 | +1 |
| 切到防火墙段 | +2（`version` + `fw.show`，已并行） |
| 切到公钥段 | +2（`version` + `keys.list`，已并行） |
| 切到定时任务段 | +1 |
| 打开 Peer 面板 | +1（`snapshot`） |

**一轮浏览最多约 9 个 Worker 请求**，加上每 10 秒一次快照轮询（有域名的节点走直连，
没有的走 Worker）。配额压力主要来自轮询，不是页面加载。

## 5. 我的建议（与提案的差异）

### 5.1 直连范围收窄

提案的 `ops-read` 有 9 个动词，我建议改成 **7 个**：去掉 `keys.list` 与 `svc.logs`。

理由：通道分类的价值在于「一条规则能放心地用一辈子」。为了多快 5 个动词而把
「谁有登录权限」和「日志内容」放进直连通路，是不划算的交换。这两个本来也不是
高频操作（公钥页很少开、日志是按需看）。

### 5.2 先算清楚收益再动手

`ops-read` 里真正的耗时大头：

| 动词 | 耗时 | 省下直连的意义 |
|---|---|---|
| `processes` | 120–190 ms | **唯一大头**，但其中 100ms 是采样窗口，省不掉 |
| `logs.errors` | 66–72 ms | 跑 `journalctl`，与通道无关 |
| 其余只读动词 | **< 1 ms** | **可完全忽略** |

**这条最关键**：除 `processes` 和 `logs.errors`，所有只读动词在 Agent 侧都不到 1 毫秒。
也就是说 C2 能给它们省下的上限，就是「Worker→Hub 那一跳」的全部——几十毫秒顶天。

> 11-17 复测后这条要说得更重：**Agent 侧所有只读动词（除进程与错误日志）都不到 1ms。**
> 所以 C2 的收益上限 = 「Worker→Hub 那一跳」的全部耗时，没有别的可省。
>
> 而用户感知的页面加载时间由这几段构成：
> `TLS 首次握手 800ms` + `Caddy 处理 24–74ms` + `Worker→Hub 一跳（待测）` + `Agent < 1ms`。
>
> **Agent 已经是整条链路上最快的一段。继续在 Agent 上优化、或者为它加一条直连，
> 收益都取决于「Worker→Hub 那一跳」有多长。这个数没测出来之前，C2 不该开工。**

### 5.3 但有一件事值得独立做

不管 C2 做不做，**「按类别声明通道」这个规则本身该写下来**（提案 C1）。
现在的情况是：新增一个只读动词时，没有任何东西告诉开发者它该走哪条通道，
也没有测试能拦住「把写动词标成只读」这种错误。这是治理问题，与性能无关。

## 7. 我的推荐顺序

1. **先做 C1（写规则）** —— 这是治理问题，与性能无关，且越晚做新增动词越乱。
   同时把 §2 的分类（`ops-read` 7 个、`control` 9 个、排除 `keys.list`/`svc.logs`）写进 ADR。
2. **再量化 Worker→Hub 那一跳** —— 这是 C2 唯一的收益来源，测一次就有答案。
3. **C2 只在那一跳超过 150ms 时做** —— 否则不做，转去查 Caddy 的 24–74ms
   （那个每个请求都付，收益覆盖全部请求）。
4. **Peer 数据无论 C2 做不做都不受益** —— 需要单独考虑 Peer 面板的体验。
