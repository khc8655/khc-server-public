# plan: 设置信息架构重组（账号/域名/双轨证书）与安装发布主流程

> 状态：草案 ｜ 最后核验：2026-11-21 ｜ 关联：docs/ui-redesign/page-specs.md、docs/design-v3.md、docs/hosted-apps.md

## 1. 背景与现状问题

基于 2026-11-21 对生产面板（`v0.24.1`）全链路走查，以下 4 类概念与入口问题仍影响日常使用：

1. **账号与域名未分层**：设置页「域名」把 DNS 凭据（API Token）与 Zone/解析记录/节点绑定混在同一卡片里，后续接入腾讯云、阿里云等其他 DNS 服务商时语义会更混乱。
2. **全局证书语义割裂**：当前全局「证书库」只是 D1 里的 PEM 存储表，控制面本身没有 ACME 签发能力，签发/续期仍借某台 VM 上的 `acme.sh`；而普通站点 `tls=auto` 由 Caddy 自签自续。如果使用全局证书，VM 不应再强依赖 `acme.sh`；同时接入层又需要保留在 VM 本地安装 `acme.sh` 或签发自签 IP 证书的通道。
3. **「应用管理」与「应用目录」重复**：两张 Tab 看的都是 `magpie` 这类控制面适配清单，纯属重复入口。
4. **两条高频主流程不够直达**：安装托管应用目前藏在节点「应用 → 添加站点 → 目标来源=本机 → 上游来源=应用目录」里，首次使用很难发现。

## 2. 方案对比与推荐

### 2.1 全局设置重组：账号 / 域名管理 / 双轨证书 / 应用管理

- **拆分「账号」与「域名管理」**
  - **账号**：集中管理 Cloudflare Token（及后续腾讯云、阿里云等 DNS 凭据），只做新增、编辑、删除、权限测试，不混放解析记录。
  - **域名管理**：基于已配账号拉取可用域名（Zone），提供添加/修改/删除记录、DoH 解析生效检测、与节点（VM）绑定关系展示，以及引导前往绑定或发布站点。
- **双轨证书（推荐：控制面 DNS-01 签发为主 + 保留 VM 本地 `acme.sh` / IP 自签）**
  - **方案对比**：
    - 仅靠 VM Caddy/acme.sh：国内机或无 80/443 机器难以泛域名复用，全局证书库失去意义；
    - 全砍掉 VM acme 能力：无法覆盖裸 IP 节点自签 TLS 证书或单机自管证书场景；
    - **推荐（双轨并行，按节点/站点所选模式解耦）**：
      1. **控制面原生 ACME v2 DNS-01 签发**：在 Worker 内用 WebCrypto + JWS + 已配置 DNS 账户自动写/删 `_acme-challenge` TXT，直接签发单域名或泛域名证书（如 `*.khc66.top`）并存 D1；站点或节点选用「全局证书」时，控制面下发证书与私钥到目标 VM，**该 VM 免装 `acme.sh`**（也不报缺失 `acme.sh` 告警）。因不做 Cron 自动续期，临期 ≤14 天进首页「需要处理」，点击即用控制面 DNS-01 重签并同步到引用节点。
      2. **保留 VM 本地证书能力**：继续保留节点设置/命令生成里的「安装 acme 工具（可选）」与 **IP 自签证书** 能力，及站点 Caddy `tls=auto`（80/443 自动续期）。仅当节点或证书记录本身声明依赖本地 `acme.sh` 时，诊断才检查 `acme.sh` 是否就绪。
- **只留「应用管理」，移除全局「应用目录」**
  - 全局设置只保留 **「应用管理」**（维护平台适配的应用清单、安装/卸载脚本与版本，例如 `magpie`），下线冗余的只读「应用目录」Tab（旧 `/settings?tab=catalog` 兼容回落至「应用管理」）。

### 2.2 两条核心主流程收敛

1. **流程 1：添加域名并接入 VM**
   - 第 1 步（账号）：配好 Cloudflare / DNS 账户 Token；
   - 第 2 步（域名管理）：拉取并启用域名 → 添加 A/AAAA/CNAME 解析指向目标 VM IP → 点击「检测解析」确认公网生效；
   - 第 3 步（节点）：新增或编辑节点（VM）时直接选取该域名绑定（已有账号但未加域名可就地添加，无账号时保留手填域名兜底）。
2. **流程 2：VM 内安装应用并发布**
   - 在 **「节点 → 应用」** 页头提供显式一等动作 **「安装并发布应用」**（与手工「添加站点」并列）：
     - 第 1 步 **选应用**：列出「应用管理」已启用的适配应用（标注已装状态）；
     - 第 2 步 **简配置**：渲染该应用必要参数 + 访问域名（可从节点域名/证书域名选择或手填）+ 对外端口 + TLS（全局证书 / Caddy 自动签发）；
     - 第 3 步 **安装并发布**：触发安装并流式展示日志 → 读取清单声明/实测监听端口 → 自动写入 Caddy 站点配置并执行 `apply`（发布失败不静默吞错，明确提示已装好应用与站点错误，可直接重试发布或去清理）。

## 3. 范围与不做

- **本提案范围**：设置页结构调整（账号 / 域名管理 / 证书 / 隧道 / 应用管理 / SSH 公钥 / 系统变量）；Worker 侧 ACME v2 DNS-01 签发/续期与既有路由兼容；VM「安装并发布应用」向导；诊断告警解除对使用面板证书 VM 的 `acme.sh` 强绑定。
- **明确不做**：不做后台 Cron/定时器自动续期证书；不做多用户/多租户 RBAC；不改 `agent/khc/` 核心加密协议与通道模型；本期不实现除 Cloudflare 之外的具体云厂商 DNS HTTP 驱动细节（仅预留账号类型与驱动接口）。

## 5. 待拍板项

1. **云厂商账号接入节奏**：S1 是否在「账号」页先只提供「Cloudflare」可用类型（同时界面/模型预留多服务商结构，腾讯云 DNSPod / 阿里云 DNS 在后续独立批次补驱动），避免空选项困扰？**（推荐：是，先只列已支持的 Cloudflare）**
2. **证书续期后的节点同步策略**：控制面续期某张全局证书后，是由用户点击按钮「同步到 N 个关联站点」（显式下发 `apply`），还是自动对所有在线引用节点触发？**（推荐：续期界面显式列出受影响站点并提供一键「同步到关联站点」按钮，避免自动重启未预期的节点服务）**
3. **手工「添加站点」的精简程度**：S2 独立出「安装并发布应用」主按钮后，原「添加站点」抽屉内是仅保留「本机端口 / Peer / 自定义上游」，还是仍保留一个去应用目录的快捷跳转？**（推荐：只留端口/Peer/自定义，并在「本机」旁放一句去「安装并发布应用」的引导链接，减少两套重复表单）**
