# 应用清单与分发分离（提案）

> 状态：已拍板（2026-11-15，范围收敛为「只做架子」） ｜ 最后核验：2026-11-15 ｜ 关联：`docs/design-v3.md` §3.5、`docs/security-boundaries.md`、`agent/khc/recipes.py`

> **执行者须知**：本提案**只交付架子**——应用管理入口、脚本存储、下发与降权执行通道。不编写、不验证任何具体应用的适配脚本；具体脚本以后由主人在面板里逐步添加，不属本提案批次。§8 已全部拍板，合并后按 §9 从 R1 开工，一个批次一个 PR。

## 1. 背景与主人的目标

主人 2026-11-15 的最终范围（17:50 收敛）：

1. **只做架子**，后面慢慢适配脚本。装什么内容不重要，本提案不涉及。
2. **面板要具备「应用管理」入口**。
3. **以后添加脚本不用再发版** —— 不发布新版 Agent，也不重新构建面板。

现状（main `3322489`）里挡住第 3 条的有两处：

| 环节 | 现在 | 为什么必须改 |
|---|---|---|
| 应用定义 | `agent/recipes/catalog.json` + 各应用 `install.sh`，随 Agent 包发布 | 加一个应用就要发 Agent 新版 |
| 面板目录 | `apps/web/src/apps/catalog.generated.json`，由 `scripts/gen-app-catalog.mjs` 在构建期生成 | 加一个应用就要重建面板 |

可复用的现成能力：`agent/khc/recipes.py` 的 `KHC_PARAM_*` 环境变量传参、`KHC_RESULT=` 结果回传、`installed.json` 已装记录、写盘白名单、后台任务；`agent/khc/util.py` 的 `Paths` 已支持 user profile。

## 2. 目标架构

```
面板「应用管理」──CRUD──▶ Worker ──▶ D1 表 app_manifests（脚本正文 + 元数据）
面板「安装」──▶ Worker：取脚本 + 参数 ──HMAC──▶ Agent
                                                  │ 以专用普通用户执行
                                                  ▼
                         脚本自行决定装什么 / 怎么配 / 怎么起服务
```

- **分发的是脚本，配置的是参数。** Agent 不解释应用语义，只负责安全地把脚本交给降权执行器。
- 脚本正文存在 D1，安装时由 Worker 随请求下发；**Agent 里不再内置任何应用清单或脚本**。
- 面板目录改为运行时从 Worker 读取，删除构建期生成链路。
- **这套通道必须一次做对**：以后新增/修改脚本只改 D1 数据，不再动 Agent、不动面板。

## 3. 数据形状（架子，非具体应用）

字段示意，具体取值由以后添加脚本时填：

```json
{
  "id": "...", "name": "...", "version": "...",
  "runtime": { "user": "...", "linger": true },
  "params": [ { "key": "...", "type": "string", "default": "" } ],
  "scripts": { "install": "...", "uninstall": "..." },
  "sha256": { "install": "...", "uninstall": "..." },
  "writes": [ "..." ]
}
```

**Agent 侧固定规则（脚本不能改）**：

- 脚本落盘前按 `sha256` 校验；不一致即中止，不落盘、不执行。
- 参数经 `KHC_PARAM_*` 环境变量传入，不拼命令行、不进日志；沿用 `KHC_RESULT=` / `KHC_RESULT_FILE`。
- 写盘白名单由 Agent 判定，`writes` 必须落在允许根内，防符号链接逃逸（复用 `assert_safe_path`）。
- 脚本以 `runtime.user` 指定的普通用户执行，不以 root（见 §4）。
- 动作：安装、更新（换脚本与 sha256）、卸载、重启、状态、最近日志。
- 支持多实例，各自独立用户或独立 `XDG_*` 根目录。

## 4. 运行身份：整套降权（已拍板）

这是「不签名」得以成立的前提，**不是给 unit 加一行 `User=` 就算数**：

1. **脚本执行**：Agent 以 `runuser -u <runtime.user> -- bash <script>`（或等价调用）执行，脚本进程本身不是 root。R1 必须实测 `ctx.run` 降权、`KHC_*` 环境变量是否完整传递。
2. **应用进程**：由脚本自行创建的用户级 unit（`~/.config/systemd/user/`）以该用户运行。
3. **无人登录仍运行**：`loginctl enable-linger <user>`。目标机实测 `Linger=no`，这是必做步骤。
4. **Agent 沙箱要开口子**：现 unit 为 `ProtectHome=read-only` + `ProtectSystem=full`，`ALLOWED_WRITE_BASES` 全是系统根。需新增受控家目录根并同步扩大 `ReadWritePaths` —— **开口范围就是新攻击面，R1 要给最小集合并列成清单**。

> 目标机已核实：systemd 255、`systemctl --user` running、`/run/user/1001` 存在、`loginctl` 可用、`Linger=no`。

## 5. 存储与接口

- D1 新表 `app_manifests`：`id`、`manifest_json`、`version`、`enabled`、`updated_at`。不设 `signature` 字段（已拍板不签名）。属于配置，符合「D1 只存配置」。
- Worker：`GET/POST/PUT/DELETE /api/v1/app-manifests`，写入时用 `packages/contracts` 的 schema 校验并拒绝未知字段。
- 安装：`POST /nodes/:id/apps/app-catalog/recipe_install` 参数从 `{recipeId, values}` 扩展为 `{manifest, values, instance}`，manifest 由 Worker 从 D1 读出后附上，**不接受浏览器直接传入**。
- 已安装记录仍落节点 `installed.json`（0600），观测仍走 `/state`，不新增轮询。
- 现有 `catalog.json` 内置 recipe **原样保留、本提案不动**；等以后脚本迁移完成后再单独处理。

## 6. 安全口径（已拍板：不签名，靠审计）

- **如实说明**：脚本以专用普通用户执行后，改脚本不再等于「拿到节点 root」。但仍能以该用户身份读写白名单内目录、运行其进程；若多个应用共用用户或家目录根，可横向影响。降权**缩小**了爆炸半径，不等于没有风险。
- **不签名的补偿措施（缺一不可）**：
  1. 新增/修改/删除脚本都写 D1 `audit`，记录操作者、时间、应用 id、脚本新旧 sha256；
  2. 面板抽屉展示脚本 sha256，换脚本时显式展示新旧差异；
  3. 每个应用独立 `runtime.user`，禁止共用；
  4. 脚本落盘前校验 sha256，节点侧再校验一次，不一致不执行；
  5. 参数中的 secret 不进日志（复用 `_redact`）；
  6. 生产上线前开启 TOTP（测试期不开，延续既定决定）。
- `release_verify.py` 的 Ed25519 验签能力保留但不启用；日后收紧需重新拍板。

## 7. 面板「应用管理」入口（核心交付）

归类为全局设置下的「资源库」页面类型，复用现有列表加单抽屉范式：

- **入口**：全局设置中新增「应用管理」导航项，登记到 `routes.ts` / `actions.ts` / `page-specs.md`。
- **列表**：名称、版本、运行用户、已安装节点数、状态（启用/停用），整行可点；空态引导「添加第一个应用」。
- **抽屉**：编辑脚本正文与元数据，失焦按 schema 校验并标出错误位置；展示脚本 sha256；右侧预览由 `params` 生成的安装表单。
- **操作**：新增、复制为新应用、停用（已安装的不受影响）、删除（仍有节点装着时禁止）。
- **节点「应用」页**：选应用、实例名、参数 → 安装；之后可更新、重启、卸载、看日志。
- UI 改动的执行 PR 附浅色、深色、390 宽截图与四态说明。

## 10. 风险与 R1 待验证

- **通道要一次做对**：R1 之后新增脚本只改 D1，若执行通道留了需改代码的口子，就违背「不用再发版」。
- **`ctx.run` 降权可行性未验证**：Agent 在 `ProtectSystem=full` 沙箱内，能否稳定执行 `runuser` / `systemctl --user` 需实测；若不可行改用 `systemd-run --user` 一次性单元，**不退回 root**。
- **linger**：`Linger=no` 已实测，未 `enable-linger` 时用户退出后服务会停，易误判成「装好了但没跑」。
- **降权不等于无风险**：共用用户、家目录根过大、脚本读宿主敏感路径都会重新扩大攻击面，R1 要给最小集合。
- **未测**：Tunnel 节点 user unit 行为、arm64 兼容性、多实例共用 `XDG_RUNTIME_DIR` 的冲突。这些不阻塞架子交付，按需要在后续验证。
