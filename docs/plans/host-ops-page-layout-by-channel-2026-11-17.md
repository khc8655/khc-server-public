# 主机运维页：要不要按「直连 / 非直连」重排？（2026-11-17）

> 状态：分析结论（不建议重排）｜最后核验：2026-11-17
> 面板 0.17.3 / Agent 0.5.2 ｜ 关联：ADR-0020、PR #75 §3、PR #76

## 0. 结论

**不建议按通道重排页面。** 五个段里有三个天然是混合的，强行拆分会让用户更难用，
而且拆完省不到时间——因为真正的瓶颈不在通道（见 §3）。

这个结论与 PR #75 §3 一致（那里已经否掉了「按页面分」），本文补充**实测数据**
和**为什么连「把同类的放在一起」也做不到**。

## 1. 五段的类别构成（按代码核实）

| 段 | 数据 | 类别构成 | 性质 |
|---|---|---|---|
| 状态带（顶部） | `status`、`snapshot`、`version` | 全直连 | **纯直连** |
| 服务 | `svc.list` + `svc.restart`、`svc.reset-failed`、`svc.logs` | 1 读 + 3 写 | 混合 |
| 进程 | `snapshot`、`processes` | 全直连 | **纯直连** |
| 防火墙 | `fw.show` + `fw.apply`、`fw.confirm` | 1 读 + 2 写 | 混合 |
| 公钥 | `keys.list`、`keys.add`、`keys.remove` | 全控制面 | **纯控制面** |
| 定时任务 | `cron.list` + `cron.set` | 1 读 + 1 写 | 混合 |

**3 个混合、1 个纯直连、1 个纯控制面。** 只有「状态带」和「进程」「公钥」能按类别归位，
而这已经是现状了。

## 2. 为什么「把直连的放一起」做不到

### 2.1 读和写长在同一个 UI 单元上

这是最硬的一条。写操作不是独立页面，而是**数据行上的按钮**：

- 服务段：每个服务行有「重启」「清除失败状态」
- 公钥段：每个公钥行有「删除」
- 防火墙：规则列表上方有「应用」，每行有编辑

数据（只读）和它的操作（写）是**同一行的两个部分**。要把它们分到不同区域，
只能拆成「只读列表」+「操作面板」，用户得在两处之间来回对照
——「我要重启的是第 3 个服务」这种对应关系会立刻变得不可靠。

### 2.2 服务段和公钥段拆不开

- 服务段：`svc.list`（可直连）+ 3 个写动词（必须控制面）
- 公钥段：全是控制面。**它压根没有「直连部分」可拆**

所以按类别重排的结果是：服务段被劈成两半、公钥段原地不动、防火墙和定时任务同理。
**五个段里四个要重排，而收益是零**（见 §3）。

### 2.3 拆完还要多付一次请求

现在的形态是「进段时取一次数据」。拆成「只读区 + 操作区」之后，如果两块各自取数，
就多了一次通道往返。ADR-0020 的四条准入条件里第 4 条要求「降级后结果完全一样」，
而拆开会让两块的数据来自两个时刻——**状态不一致的风险反而上升**。

## 3. 最关键的：拆了也快不了

按 PR #76 的实测，host-ops 只读动词在 Agent 侧：

| 动词 | 耗时 |
|---|---|
| `svc.list` | 0.8 ms |
| `fw.show` | 0.7 ms |
| `cron.list` | 0.5 ms |
| `version` | 0.6 ms |
| `processes` | 120–190 ms（其中 100ms 是 CPU 采样窗口） |

**除进程列表，全部在 1 毫秒以内。**

而用户感知的页面加载时间是：

```
TLS 首次握手 800ms（只首次）+ Caddy 处理 24-74ms（每请求）+ Worker→Hub 一跳（待测）+ Agent <1ms
```

**Agent 是整条链路上最快的一段。** 为了给这段不到 1ms 的数据开直连，去重排整个页面
的布局，性价比是负的。

> 一句话：现在页面慢，和「数据走哪条通道」基本无关。

## 4. 那什么值得做

如果目标是「让主机运维页更快」，按收益排序：

| 优先级 | 做什么 | 预计收益 | 影响范围 |
|---|---|---|---|
| 1 | **量化 Worker→Hub 那一跳** | 决定 C2 做不做 | 全部请求 |
| 2 | **查 Caddy 的 24–74ms** | 每请求都省 | 全部请求 |
| 3 | 减少段切换时的重复请求 | **已确认没有可省的**（见 §4.2） | — |
| 4 | C2 直连只读运维 | 上限 = Worker→Hub 那一跳 | 7 个动词 |
| — | ~~按通道重排页面~~ | **0（还要多付请求）** | — |

### 4.1 一个查了但**否掉**的想法：用 `snapshot` 取代 `version`

我本来以为这里有收益：`version` 在防火墙段和公钥段各取一次，而 `snapshot` 的返回里
已经有 `version` + `root`（`khc_host.py:909-913`），所以那两次 `version` 是多余的，
应该能省。

**实测否掉了。** U6 已经把 `version` 和 `fw.show`/`keys.list` 改成并行了，
所以现在已经是「一次往返」。换成 `snapshot` 仍然是「一次往返」，**收益为零**：

```
snapshot   0.5-0.7 ms（稳态）
version    0.5-0.7 ms（稳态）
```

> 这是并行化已经把这条路走完的例子。省「重复取数」的前提是两次取数**串行**；
> 一旦并行，多取一个几乎免费的数据就不再是问题。

### 4.2 页面加载本身没有浪费

逐段核查了加载函数：

| 文件 | `await callHostOps` | `Promise.all` | 说明 |
|---|---|---|---|
| `OpsSegments.tsx` | 12 | 1 | 其中 **7 个是用户触发的写操作**（重启、改 cron、增删公钥），只有 5 个是加载，每个组件各取一次 |
| `FirewallSegment.tsx` | 2 | 1 | 已并行 |
| `SshKeysDrawer.tsx` | 2 | 1 | 已并行 |
| `ProcessDrawer.tsx` | 1 | 0 | 只取一次，无需并行 |
| `PeerOpsPanel.tsx` | 1 | 2 | 已并行 |

**结论：没有残留的串行加载。** U6 那轮已经把该并的都并了。
所以「减少请求」这条路也已经走到头了。

## 5. 那 UI 上该做什么（如果一定要动）

**只做一件事：把通道状态显示清楚，不重排布局。**

U1 已经在节点栏做了「实时 · 直连 / 实时 · 经控制面」的指示。可以再补一句展开说明，
按类别列出（观测 / 只读运维 / 变更），让需要排查的人能看到，**普通用户不需要理解**。

这符合 PR #75 §5 的设计：用户不需要选通道，也不需要理解三个类别。

## 6. 结论复述

- **不要按通道重排页面。** 3/5 的段天然混合，读写长在同一行，拆了还要多付请求。
- **不要为 0.5ms 的数据开直连。** Agent 侧已经是链路最快的一段。
- **要做的是**：量化 Worker→Hub 那一跳、查 Caddy 开销、去掉重复请求。
- **UI 只补说明，不改布局。**
