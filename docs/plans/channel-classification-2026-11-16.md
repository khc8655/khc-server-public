# 浏览器直连与控制面：通道分类（提案）

> 状态：待拍板 ｜ 最后核验：2026-11-16（main `dcc5f4f`，面板 0.17.1 / Agent 0.5.0） ｜ 关联：ADR-0009、ADR-0010、ADR-0012、`docs/live-observation.md`、`docs/host-ops.md`、`docs/data-layering.md`、`apps/web/src/apps/host-ops/connectionState.ts`

> **约束**：本文只给方案和实测方法，不改代码。§6 拍板后，先做 S0（只出证据），再按 S0 的结论决定 C1/C2 做不做。标了「待 S0 验证」的地方都还没有实测，不能当作推荐依据。

## 0. 来源

主人 2026-11-16 提的问题：「浏览器直连获取 VM 信息这部分，现在的方案是不是最佳？到底哪些数据或界面走直连，哪些经面板？是按页面分还是按功能分？没有域名和 HTTPS 的节点，运维要不要禁掉？怎么分才不乱、好维护，用户也容易理解？」

## 1. 现状（代码核查）

| 数据 | 通道 | 依据 |
|---|---|---|
| 指标（CPU、内存、磁盘、负载）、失败单元，每 10 秒一次 | 有 HTTPS 域名：浏览器直连 `https://<domain>/_live/snapshot`（`snap` 票据，15 分钟内可复用）；没有：经 Worker `/nodes/:id/snapshot` 转发 | `apps/web/src/data/snapshot.ts`、ADR-0010 |
| 服务列表、进程、防火墙查看、公钥列表、定时任务列表、服务日志、近 24 小时错误 | 一律经 Worker（`host-ops/call`），和有没有域名无关 | `apps/web/src/data/hostOps.ts` |
| 适配器状态、端口、站点、Peer 握手 | 打开工作区时经 Worker 取一次 `/state` | ADR-0009 |
| 全部写操作、配置、密钥、跨节点汇总 | 经 Worker | — |

已经有的东西：
- Agent 观测服务（`agent/khc/live.py`）目前只认三种票据作用域：`live`、`nudge`、`snap`。
- 节点栏的连接指示（U1，`connectionState.ts`）已经能显示「实时 · 直连 / 实时 · 经控制面 / 离线」，并可以展开查看每类数据实际走哪条通道。
- host-ops 动词已经分成了读和写：`PUBLIC_VERBS` 与 `WRITE_VERBS`（#63），只读动词不抢写锁。
- #72 之后，本机调用改为进程内执行，Agent 侧的耗时：`version` 约 2ms，`svc.list` 约 8ms，`fw.show` 约 11ms，`processes` 约 120–190ms（其中 100ms 是 CPU 采样窗口）。

## 2. 问题

1. **没有成文的规则。** 「哪些数据可以直连」只体现在 ADR-0009/0010 对快照的特例里。新增功能时只能靠写代码的人自己判断，而判断的依据（只读、敏感、配额）没有写在任何一处。
2. **真正的耗时没有测过。** S0（`docs/verification/2026-11-16/ui-polish-s0.md`）和 #71–#73 测的都是 Agent 本机的耗时，「浏览器 → Worker → Agent」这一段的公网往返从来没有测过。Agent 侧已经压到个位数毫秒，用户感受到的慢，大概率就落在这一段（**待 S0 验证**）。
3. **配额。** 主机运维页每次打开、每次刷新，都要经 Worker 发出 5–7 个请求。ADR-0009 当初要避开的配额消耗，现在又从主机运维这条路回来了。

## 3. 分类粒度

| 选项 | 做法 | 问题 |
|---|---|---|
| A 按页面 | 一个页面只用一条通道 | 不成立。主机运维页既有只读列表，也有重启、改防火墙这类写操作，而写操作必须经控制面，所以一个页面注定是混合的 |
| B 按功能逐个指定 | 每个列表、每个按钮各自决定通道 | 准确，但规则会散落在前端各处。新增功能时容易漏判，用户也看不懂为什么同一页有的快、有的慢 |
| **C 按数据类别声明，按页面展示（推荐）** | 每个 Agent 动词只声明一个类别，通道由类别决定；界面只在节点栏展示一个汇总状态 | 需要改冻结核心（见 §5） |

### 3.1 方案 C 的三个类别（只有这三个）

| 类别 | 包含 | 通道 |
|---|---|---|
| **观测**（`observe`） | 指标、失败单元、Peer 握手、端口占用 | 优先直连，不通时经控制面 |
| **只读运维**（`ops-read`） | `svc.list`、`processes`、`fw.show`、`keys.list`、`cron.list`、`svc.logs`、`logs.errors`、`status`、`version` | 优先直连，不通时经控制面。**是否真的迁移，由 S0 决定** |
| **变更与机密**（`control`） | `WRITE_VERBS` 里的全部动词、应用安装与配置 apply、证书、含 Peer 私钥的客户端配置（`client_config`）、全局概览与节点列表 | 只经控制面，永不直连 |

判定规则只有一条，四个条件同时满足才能进入前两类：
1. 只读，不改变节点状态；
2. 不含私钥、密码这类拿到就能直接使用的秘密；
3. 不需要 D1 里的数据，也不需要跨节点汇总；
4. 直连失败时能改由控制面转发，并且拿到的结果完全一样。

### 3.2 怎样保证不乱

- **只有一份权威。** 类别作为动词注册表里的一个字段（host-ops 写在 `khc_host.py`，其他适配器写在各自 `actions` 的声明里），并导出到 `packages/contracts`。前端和 Worker 都从这里读取，不再各自维护一份列表。
- **新增动词必须填类别。** 没填就注册不了，单测会直接失败。
- **安全兜底测试。** `WRITE_VERBS` 里的动词如果被标成了 `observe` 或 `ops-read`，测试失败；Agent 观测服务收到 `control` 类别的请求，一律拒绝（双重保险）。
- **票据作用域与类别对应。** Worker 签发票据时写入 `s=snap` 或 `s=ops-read`，Agent 按作用域放行。`control` 类别没有对应的票据，因此不可能直连。
- **前端不写任何「这个功能走哪里」的判断。** 统一调用一个取数函数（例如 `readNode(hubId, verb, params)`），由它根据类别选通道并负责降级；写操作仍然走现有的 `host-ops/call`。

## 4. 没有域名或没有 HTTPS 的节点

| 选项 | 结果 |
|---|---|
| D1 整个运维禁掉 | 不建议。写操作本来就不依赖直连，禁掉并不会更安全，只会让节点在刚接入、还没配域名的时候无法管理 |
| D2 禁掉部分功能（例如自动刷新） | 不建议。用户只会看到一些功能莫名其妙地缺失 |
| **D3 功能不变，通道自动改走控制面（推荐）** | 就是快照现在的做法（ADR-0010）。数据内容和直连完全一致，只是慢一些、要消耗 Worker 请求额度 |

D3 的附带决定：经控制面时，10 秒快照轮询是保持不变，还是放宽到 30 秒以节省额度（见 §6 第 2 问）。

只有 HTTP 的地址：从 HTTPS 面板访问时浏览器会因为混合内容直接拦截。代码里已经用 `isHttpsEndpoint` 按「没有域名」处理了，不用改。

## 5. 用户看到什么

- 用户不需要选通道，也不需要理解这三个类别。
- 每个节点只有一个状态，放在 U1 已经做好的连接指示里：「实时 · 直连」或「实时 · 经控制面」。悬停时说明原因，例如「未配置 HTTPS 域名」或「直连不可达，已自动切换」。展开后的明细按类别列出，不再按页面列。
- 写操作永远经控制面，不单独标注。
- 节点设置页加一句提示：「配置 HTTPS 域名后，观测和只读运维会更快」。

## 8. S0 实测方法（不改代码）

两条路现在都已经存在，可以直接对比：
- 直连：`GET https://<domain>/_live/snapshot?ticket=…`
- 经 Worker：`GET /api/v1/nodes/:id/snapshot`（`apps/api/src/routes/snapshot.ts`），Worker 向 Agent 取的是同一份快照。

步骤：
1. 在主人常用的网络下（家里宽带、手机热点各测一轮），打开面板并登录，在浏览器控制台里对 oracle-x86-2 交替请求两条路各 20 次，记录每次的 `performance` 耗时，求中位数和 P90。
2. 额外测一个只读运维动词经 Worker 的耗时（`POST /api/v1/nodes/:id/apps/host-ops/call`，`verb=version`），用来扣除快照本身的采集时间，得到纯通道开销。
3. 记录打开一次主机运维页会发出多少个 Worker 请求（DevTools 的 Network 面板），用来估算配额。
4. 证据写入 `docs/verification/<日期>/channel-s0.md`。

判定：
- 直连中位数比经 Worker 快 150ms 以上：做 C2。
- 差距在 150ms 以内：不做 C2，只做 C1，只读运维保持经控制面，规则照样写下来。
- 直连在任一网络下明显不稳（失败率超过 5%）：不做 C2，并在 C1 的 ADR 里写明原因。
